## v3 是什麼

使用者試過 v2（拖曳甩筒子、籤掉到地上）覺得不好，改成：

1. **籤筒固定不動**，按住籤繞圈攪；籤束跟著手在筒裡左右轉（最多 31°，放手一秒內轉回正面）、上下推擠。
2. 攪夠了提示「可以放手了」，**同時**向伺服器抽籤（號碼在這一刻定死）。之後攪多久都不影響結果。
3. **放手才抽**：前排正中那支沿自己的軸**抽出一截**（`RAISE`，籤底一直插在筒裡），比其他籤高出
   一大截，途中第 N 籤淡入 → 拿著看（微浮）→ 淡出交給籤紙。**一口氣、不頓**：只有一個速度峰，
   見 [`plans/2026-09-23-cylinder-pull-smoothing.md`](plans/2026-09-23-cylinder-pull-smoothing.md)。
   鏡頭輕推到「籤頭貼上緣、筒口與杯面 GOOD LUCK 貼下緣」（`closeUpShot`）。
   **不要改回整支抽出、推到只剩籤**：使用者說「籤筒往下移消失、只剩籤，感覺很怪」。
4. 外觀照參考圖（奶油色日系籤筒）：20 支排成前中後三排的扇形、杯面圖案撐滿、坐著抱梅花的垂耳狗、底部圓角。

| 模組（`src/shared/cylinder/`） | 管什麼 |
|---|---|
| `geometry.ts` | 杯身尺寸與截面、**三排扇形**排布（`bundleSlot` / `stickPose`）、被拿起來那支 `PULL_INDEX`、杯身貼圖的弧長 UV（`cupArcU`） |
| `stir.ts` | 手 → 籤束轉角、強度、攪動量（取代 v2 的 `shake.ts` + `aim.ts`） |
| `pick.ts` | 攪的時候手撥過哪支籤、那支被撥起來多高；換一支響一聲（「挑到每一支籤」） |
| `bundle.ts` | 攪的時候籤上下推擠（v2 的棘輪爬升、中籤那支自己爬出去都拿掉了）；放手後其他籤歇下來 `settleStep` |
| `pull.ts` | 拿籤的時間軸與路徑（單峰 `surge`）、號碼淡入 `numberFade`、旁邊籤被帶動、**聲音 cue**（`pullCues`） |
| `framing.ts` | 待機鏡頭（含透視）、近拍 `closeUpShot`、拿籤全程鏡頭 `pullCamera`（推近／視線兩個通道） |
| `interaction.ts` | 出籤期間收不收手勢、開始抽籤放什麼聲音、籤紙出來要不要放鈴聲 |

刪掉的：`shake.ts`、`aim.ts`、`eject.ts`，以及落地俯拍 `revealShot`、筒子淡出 `revealCupFade`。

## v3 踩過的坑（都是實測抓到的，不要改回去）

1. **籤自己跑出來、穿插整個籤筒。** v2 的籤爬到筒口就交給自由落體，帶著初速與三軸旋轉翻出去，
   沒有碰撞。扇形之後更糟：籤沿傾斜的軸往上爬，筒口那一段每爬 1 單位就往外頂 0.33。
   正解是 `pull.ts` 照劇本走的路徑，測試逐格保證筒口以下那段不穿內壁。
2. **照號碼去拿外圈那支，一轉直就撞進往外傾的鄰居。** 筒裡的籤不印號碼，所以實體上永遠拿
   `PULL_INDEX`（筒心、最直、前半邊）—— 其他籤都往外傾、離它而去。號碼揭曉時才印上去，
   永遠是伺服器那一個（`sheet.stick.no`）。
3. **籤頭衝出畫面頂端、鏡頭才追上去。** 鏡頭曾用固定時間表（1.0 秒才推），籤卻在 0.3～1.3 秒
   就升了七個多單位。第二版把鏡頭進度綁死在籤頭高度上，框是框住了，但籤一衝鏡頭就跟著衝
   （推近峰值 43 u/s）。現行：推近走自己的慢時間表，**視線高度由站多遠反解**，讓籤頭釘在
   畫面上預定的高度。框得住靠「浮的進度 ≤ 上升進度」這條不等式（`pull.ts` 用同一條曲線拉長
   來保證），不要把浮改成別的曲線而不重驗 `cylinder-framing.test.ts`。
4. **聲音沒跟畫面對齊。** (a) `FortuneGame.draw()` 用 `vessel === 'cylinder'` 選音效，3D 籤筒
   `'cylinder3d'` 掉進預設分支，放的是印表機按鍵聲 + 馬達；(b)「抽到了」的鈴聲等籤紙出來才響，
   晚了將近 3 秒。正解：`drawStartSound` / `chimeAtSlip`，與 `pullCues` —— 鈴聲跟換號碼貼圖用
   同一個判斷（`ms >= NUMBER_AT`），不管幀距多亂都是同一格。
5. **杯身的字一直被拉扁。** 貼圖 u 是照**角度**鋪、畫布卻是正方形，一圈周長是杯高的 2.5 倍，
   字全被橫向拉長、越靠邊越扁。v3 第一版還在畫的時候「往回擠」，那是補丁。正解：`cupArcU` 照
   **弧長**鋪，畫布寬 = 高 × 周長 / 杯高（`TUBE_TEX_W`），一個像素在杯壁上就是正方形。
   籤身同理：`STICK_CELL_H` 由籤的真實長寬比算（v2 寫死 1024，籤上的字被拉長 1.3 倍）。
6. **籤頭的「籤」字橫躺、還被籤身蓋掉半邊。** 圓盤是 CylinderGeometry 的頂蓋轉 90° 立起來的，
   貼圖跟著轉了；且圓盤跟籤身同一個深度。正解：`headTex.rotation = π/2`，圓盤往正面挪半個籤厚。
7. **60 支擠成一團就不可愛了。** 使用者要「多一點」，但參考圖的可愛來自整齊。20 支三排扇形，
   前排 7 支正面一字排開，中排錯開半格從縫裡探出來。
8. **待機鏡頭下緣只剩 2%。** 舊算法拿世界尺寸比注視點深度的視野，忘了杯身正面比注視點更靠近鏡頭。
   正解：`idleCameraZ` 逐點用它自己的深度算。
9. **畫布填滿首屏**交給 CSS flex（`.shell:has(.cyl3d-stage)` 釘成一個螢幕高，剩下的給畫布）。
   以前組件用 JS 量「視窗高 − 畫布頂端 − 提示區」，量不到畫布**下面**的例句和頁腳，
   它們永遠被推到折線以下，要捲動才看得到。
10. **分段 ease 接縫處速度歸零 = 頓。** 每段各自先慢後快再慢，接起來就是停一下再走。
   要動的東西用一條曲線走完，其他動作寫成那條曲線的函數疊上去；測試驗速度單峰。
11. **揭曉那一格才畫畫布、傳貼圖一定掉幀。** 號碼那一面在伺服器回號碼時就先做好、
   `renderer.initTexture` 傳上 GPU，揭曉時只動 opacity。

## 驗證技巧（內建瀏覽器面板）

- rAF **和** cAF 都要墊（見下面 v2 的環境陷阱第 1 條），墊完用 vessel state 撥到 `printer` 再撥回
  `cylinder3d` 逼元件重掛，frame loop 才是活的。
- 要逐格看動畫：用**完全手動的虛擬時鐘** —— `performance.now` 回傳一個變數、rAF 只把 callback
  排進佇列、自己寫 `step(n, dt)` 推時間並清佇列。時間只在你推的時候走，分幾次 JS 呼叫都沒關係，
  截圖之間畫面不會動。要等伺服器回籤號時就不推（手按著、畫面停住），用真的 setTimeout 等。
  pointer 事件要在推時間的 hook 裡發（組件用 `performance.now()` 算手速）。
  組件內部從 canvas 的 `__reactFiber` 往上找 `FortuneCylinder3D`，hooks[1] 是 sceneRef（rig），
  有 `motions` 的那個 ref 是 Drive。
- **面板在背景時截圖會是舊畫面**：截圖前先呼叫一次 `rig.render()`，有時要 render 完**再截第二次**
  才會更新。改過視窗大小（`resize_window`）之後畫布會被清空、rAF 又被節流，看起來籤筒不見了 ——
  不是 bug，墊好虛擬時鐘、重掛組件再看。像素量測則在同一個 task 裡
  `render()` 完馬上 `readPixels`。
- 想看某個角落：停住 frame loop 後直接改 `rig.camera` 位置再 `render()`（v3 平頂方塊就是這樣抓到的）。

## 上一輪那個「搖不出籤」的死鎖 —— 已修（第 5 個 bug）

**根因不是物理，是輸入閘門。** `FortuneGame.tsx` 的 `const printing = phase !== 'ask'`
被當成籤筒的 `disabled`。籤筒抽到籤就 `setPhase('ejecting')`，於是 `disabled` 變 true，
`onPointerDown` 第一行直接 return。

閉環：輸入關掉 → `dragging` 永遠 false → `pushHand` 不被呼叫 → `intensity` → 0 →
`stepBundle` 的 `drive` = 0 → `CHOSEN_LIFT` 和 `RATCHET` 同時歸零 → 中籤那支只剩重力、
靠 `GRIP_HOLD` 慢慢沉 → 爬不到 `exitRise` → `stage` 卡在 `shaking` → `onRevealed` 不回報 →
phase 出不了 `ejecting` → 輸入永遠是關的。**解鎖條件只能靠那隻被關掉的手達成。**

對印表機和滾印，`ejecting` 期間關輸入是**對的**（動畫在演）；籤筒的 ejecting 是使用者
搖出來的。時長早就改成手勢驅動了，閘門還留著計時器驅動的假設。

正解在 `src/shared/cylinder/interaction.ts`：`isGestureDriven(vessel)` /
`acceptsGesture(vessel, phase)`。

> **舊版診斷對照表的 `climb` 那一列會誤導。** 它寫「`climb` 不長 = 物理沒推動它 =
> 回去看 bundle.ts」。這次 climb 確實不長，但 bundle.ts 是好的 —— 訊號根本沒進去。
> 看到 `climb` 不長要先看**同一行的 `drag`**：`drag n` 而使用者手按著，就是閘門問題。

那個 `?cyldebug=1` 疊層**已依使用者要求整個移除**（含 CSS 與 probe state）。
下次要再加回來，就是在 frame loop 裡每 120ms `setProbe()` 一行字，很便宜。

## 這個專案的鐵律

### 1. 可測的數學一律擠進 `src/shared/cylinder/`

不 import three、不碰 DOM，所以 vitest 直接測得到。
**每一個渲染期才看得見的錯，都是靠這條抓到的。**
不要放回 `src/app/` —— `tests/` 由 `tsconfig.worker.json` 編譯（無 DOM lib），
放錯地方會讓 `npm run check` 炸一堆錯。

目前這層有：

| 模組 | 管什麼 |
|---|---|
| `geometry.ts` | 尺寸、籤束排布、**杯身截面**、姿態常數、樞軸 |
| `bundle.ts` | 筒內籤束的降維物理 |
| `eject.ts` | 脫出那一支的自由落體 |
| `shake.ts` | 手勢 → 搖動強度與功 |
| `interaction.ts` | 出籤期間收不收手勢（死鎖那條） |
| `framing.ts` | 待機鏡頭該站多遠、**出籤那一鏡站哪裡／筒子怎麼退場** |
| `aim.ts` | 手勢方向 → 籤筒朝向（360° 搖） |

### 2. 「要多遠、要多大」用**算**的，不要用眼睛量

`framing.ts` 的距離是從籤筒的包圍範圍推出來的，測試**獨立重算一次**去驗它
（抄 framing 的答案就變成自己驗自己）。

踩過的坑：鏡頭從 18 拉近到 15.5，在縮圖上看起來還有餘裕，其實已經貼邊，
換一台螢幕的長寬比就露餡。**貼邊和差一點點切到，在縮圖上長得一模一樣。**

`MARGIN = 1.1`：不只塞得進去，四邊都要留白 —— 貼著邊就是「被框住」的觀感。

## 已修掉的坑（都是實測抓到的，不要改回去）

1. **停手就沉回筒底** —— CHOSEN_LIFT 打不過重力。
2. **改成無條件上浮** —— 矯枉過正。正解是摩擦模型：搖才鬆動（`CHOSEN_LIFT × intensity`），
   停手卡在原地（`GRIP`）。兩者要同時成立。
3. **寫問題前的搖動被記帳** —— 加了 `armed` 參數。另外 `dy/dt` 在 1ms 微抖動下會頂滿強度，
   加了 12ms 下限。
4. **真實強度只有 0.64 不是 1** —— 用真實強度曲線掃過 36 支重新定 `CHOSEN_LIFT = 21`。
5. **出籤期間輸入被關掉的死鎖** —— 見上。
6. **籤筒轉到接近水平時，36 支會一起飛出筒外** —— `bundle.ts` 的註解白紙黑字寫著
   `RATCHET × climb_max` 必須小於重力沿軸分量。筒子一放倒那個分量就掉，不等式破了。
   正解：`RATCHET` 和 `CHOSEN_LIFT` 改成**隨當前軸向重力等比例縮放**（`REF_AXIS_GRAVITY`）。
   傳統角度下數值一模一樣，既有調校全部不受影響。
7. **繞筒底轉，一放倒就整支甩出畫面** —— `tiltGroup` 的原點是筒底，倒下去筒口會掃出
   半徑等於**整支長度**的圓弧。正解：繞**中段**轉（`PIVOT_X/Y/Z`），掃出的半徑減半，
   任何角度的包圍範圍都差不多大。
8. **為了做矮胖而壓高度，把物理尺度壓扁了** —— 爬升距離縮到三分之一而力道沒跟著變，
   中籤那支 **0.2 秒**就飛出去，普通籤也差點被搖出筒口（實測 0.322 對上門檻 0.35）。
   **正解：要矮胖就加粗，不要壓矮。** `TUBE_H = 6.552` 是物理尺度的基準，別動它；
   高徑比靠 `TUBE_ASPECT` 加粗筒身達成，籤跟著改成寬扁槳形（剛好就是參考圖的樣子）。

9. **出籤鏡頭那組寫死的座標** —— 見上面那一節，已改成跟著籤算。
10. **36 支籤共用同一個籤頭材質。** 出籤要把筒子淡掉時，中籤那支的籤頭跟著一起淡，
    畫面上只剩一根沒有頭的棍子。籤頭材質現在每支 `clone()` 一份。
    另外淡出的材質清單**要等真的開始淡才收**：組裝時 36 支都還在 `tiltGroup` 裡，
    那時候收會把中籤那支一起收進去，等於把主角淡掉（這個我自己先踩了一次，
    量 `chosenOpacity` 才抓到）。

## 外觀：日系黏土風，照參考圖復刻

使用者給的參考是一款奶油色日系籤筒（矮杯、圓角方柱、圓頭籤、垂耳狗）。
復刻時三個關鍵差異：

1. **形狀是圓角方柱，不是圓筒。** 正面是平的，字才立得住；圓筒的正面是彎的，
   圖案貼上去會跟著曲面變形，**怎麼調都對不上**。
   截面用超橢圓：`geometry.ts` 的 `CUP_N` / `cupRadius()` / `CUP_R_MAX`，
   網格由 `scene.ts` 的 `cupShell()` / `cupCap()` 發。
   - 法線要從截面**切線**轉 90° 算，不能用半徑方向 —— 否則四個平面會被當曲面打光，
     看起來又變回圓筒。
   - UV 起點直接定在正對鏡頭那一面（`th = u*2π - π/2`），且 `u` 要反向（截面是逆時針繞的，
     照鋪會左右鏡像）。舊版是靠 mesh 轉 180° 去湊，自己發 UV 就別再留隱形補償角。
2. **字體是圓體，不是楷書。** 這一項比任何細節都影響氣質。`materials.ts` 的 `ROUND`。
3. **狗的耳朵是掛在臉兩側的大垂耳**，下緣要低過臉的中線。畫成小圓片只會從頭頂露出
   兩個黑角，那是另一隻動物。

其餘：GOOD LUCK 寬字距、點線加紅蝴蝶結、上上籤直排、萬事順利/心想事成、四朵梅花、
籤頭雙圈「籤」、籤身圓拱框、GOOD LUCK 兩行、每支不同的小圖案（梅花/雲/富士山/鳥居/達摩）。

**兩個刻意沒照抄：**
- 杯身寫「上上籤」是照參考圖。那是籤運等級不是產品名，要換回「問籤」一行就好。
- 籤身參考圖每支都印「上上籤」，這裡放**第 N 籤** —— 抽到哪支是本體資訊，不能丟。

**版面有兩條硬限制：**
- 橫向：一個平面約佔貼圖寬度的四分之一（256px）。超出去字會爬到圓角上彎掉。
- 縱向：貼圖的 **v=0 在筒底**（畫布上方 = 杯口）。杯口被領子蓋住約 14%；
  籤只露出全長的 **38%**，畫在那條線以下的東西全都埋在筒子裡看不見
  （籤身的小圖案踩過一次）。

畫布透明、沒有案几也沒有影子（使用者要求拿掉）。頁面底色是暖木漸層（`--ground-wash`）。

## 上一輪沒驗到的那一項 —— 驗了，是壞的，已重寫（第 9 個 bug）

交接單上寫「覺得太遠或太短就調座標」。實搖之後不是遠近的問題，那組寫死的座標
`(f.x, f.y+19, f.z+9.5)` 有三個毛病，而且**兩次實搖各中一種**：

1. **籤落地的朝向是隨機的，鏡頭方位卻寫死在 +z。** `eject.ts` 躺平時只收斂俯仰
   （`rx → π/2`、`rz → 0`），**繞豎直軸那一圈不收**。轉到跟視線同方向的那一次，
   整支籤在畫面上縮成一根往深處扎的刺，字全糊了 —— 而且透視讓兩端不對稱，
   籤頭被下緣切掉（實測投影到 NDC y = **−1.11**，出界 11%）。
2. **距離是拿 `STICK_LEN` 算的，但整支籤比籤身長。** 籤頭是掛在頂端**外面**的一片
   圓盤，全長 `STICK_SPAN ≈ 11.55`，不是 `STICK_LEN ≈ 10.61`。舊座標的垂直視野
   剛好 12.08 —— 帳面上塞得下，實際上零餘裕，配上第 1 點就切頭。
3. **杯身擋在鏡頭和籤之間。** 籤是從筒口甩出去的，`vz` 還帶 +1.8 的前衝，所以
   多數落點就在筒子前面；鏡頭從 +z 回望，杯身正好卡在中間。第一次實搖就是這樣
   整個上半張畫面被杯子占掉。

正解在 `framing.ts` 的 `revealShot()`：**跟著籤算**，不是一組座標。

- 繞到籤的**側面**（視線 ⟂ 籤軸），所以不管落成什麼朝向都不會被壓縮成一根刺；
- **籤頭朝畫面上方**（`up` 直接給籤頭方向）—— 俯視時世界的 (0,1,0) 幾乎跟視線平行，
  `lookAt` 在那裡是退化的，畫面要轉多少全看浮點誤差，所以 `up` 一定要自己帶；
- 距離由 `STICK_SPAN` 算，籤直立在畫面上，所以**跟長寬比無關**（待機那顆要同時扛
  橫向才需要看 aspect）；
- 往**遠離籤筒**的那一側俯下來。

`geometry.ts` 跟著多了 `STICK_HEAD_GAP / STICK_TIP / STICK_BUTT / STICK_SPAN / STICK_MID`，
`scene.ts` 發籤頭網格時共用 `STICK_HEAD_GAP`，框景和網格不會再各算各的。

實搖驗證（兩種長寬比、兩種甩法）：整支籤含籤頭都在框內，占畫面高度 **92–94%**，
籤號讀得正。

### 杯身退場是我替你決定的，不喜歡很好改

掃過一圈落法（16 個朝向）實測：**16 個裡有 3 個**籤頭會朝回筒子，杯身正好壓在
印著「第 N 籤」那一段上。鏡頭繞不開 —— 杯身有一整支籤那麼高、就杵在旁邊三四個
單位，任何俯視角度都躲不掉（往籤頭那側倒過去只會更糟，杯子會整個插進畫面中間）。
這一鏡只有一個工作就是讓人看清抽到第幾籤，五次裡一次看不到不能算過，所以**籤一
落定就把筒子淡掉**（`revealCupFade`，停 260ms 再淡 520ms，遠早於 `REVEAL_HOLD_MS`）。

不要這個退場：把 `revealCupFade` 固定回 1 就沒了，框景照舊 —— 代價是那 3/16 的
落法會看不清籤號。想折衷的話還有一條沒走的路：鏡頭再推近、只框籤頭到籤號那一段，
杯身自然落到畫面外，但就看不到整支籤了。

## 環境陷阱（會浪費很多時間，先讀）

1. **內建瀏覽器面板是隱藏執行的，`requestAnimationFrame` 被節流到每秒 2 次**
   （`setTimeout` 正常，約 220/s），常常是直接凍住不動。任何 rAF 驅動的東西都會
   看起來像壞掉。繞法是把 rAF 換成 setTimeout 墊片，但**兩個都要墊**：

   ```js
   window.requestAnimationFrame = (cb) => window.setTimeout(() => cb(performance.now()), 16);
   window.cancelAnimationFrame = (id) => window.clearTimeout(id);   // 少這行會出鬼
   ```

   少了第二行的話 `cancelAnimationFrame(setTimeout 的 id)` 是空操作，於是
   **StrictMode 雙掛載留下的那條殭屍 frame loop 收不掉**：它跟活的那條共用同一份
   Drive ref，卻各自操作不同的 rig。它先搶到出籤那一格，就會把**它自己那個
   （已 dispose 的）rig** 的籤挪出 `tiltGroup`，活的那個 rig 的籤還留在筒裡 ——
   量出來就是「中籤那支還掛在 tiltGroup 底下」這種不可能的狀態。我為此誤判過一次，
   以為是產品的 bug。**真瀏覽器沒這問題**，`cancelAnimationFrame` 是好的。

   **墊片會跟頁面載入搶時間**：元件掛載時若抓到的是凍住的原生 rAF，鏈就斷了。
   救法（比重新整理可靠）：抓 `FortuneGame` 的 fiber，把 vessel state 撥到
   `printer` 再撥回 `cylinder3d`，逼元件重掛一次 —— 這時墊片已經在位，新的鏈是活的。
   開工前先確認 `d.current.last` 這一格會跳，不會跳就是鏈斷了，量什麼都是假的。

2. **`npm run check` 會跑完整 `vite build`，把正在跑的 dev server 洗爛。**
   worker 被反覆 HMR 之後 `/api/state` 會掛住不回，畫面卡在「正在预热打印机…」。
   **跑 check 之前先把 preview server 停掉。**

3. 使用者自己的 dev server 常佔著 5250，5173 被他另外兩個專案佔著。
   自己驗證請另開一個 port（例：5251），用完停掉。
